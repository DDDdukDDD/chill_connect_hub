# ตรวจฐานข้อมูลรอบเต็ม (8 พ.ย. 2026)

เป้า 9.5+ ตามรายการในขั้น 2 ของ [LAUNCH_CHECKLIST.md](LAUNCH_CHECKLIST.md)
ที่อ่าน: schema จริงบนฐานพัฒนา (60 ตาราง, migration 0001..0034), สถิติการใช้ตารางและ index บนฐานจริง, `pg_stat_statements` บนฐานจริง (สะสมตั้งแต่ 2 ต.ค.) ทั้งหมดอ่านอย่างเดียว และ query ในโค้ด

**คะแนนตอนตรวจ: 7.5** (หลัง BE-309/310 ราว 8; หลัง BE-312..316 วันที่ 8 พ.ย. ราว 9.5 เหลือข้อ 9 ที่เลื่อนไว้) ทำข้อ 1-4 จะได้ราว 9 ทำข้อ 5-8 ได้ 9.5 และข้อ 9 ได้ 9.5+

## ส่วนที่ดีอยู่แล้ว

- id เป็น uuid v7 เวลาเป็น timestamptz ทุกตาราง มี foreign key 110 ตัวที่เลือก cascade / set null / restrict อย่างตั้งใจ
- ค่าที่เลือกได้จำกัดใช้ CHECK, กันซ้ำด้วย unique และ partial unique (บันทึก, เยี่ยมชม, เบอร์ที่ยืนยันแล้ว)
- RLS เปิดทุกตาราง (ยกเว้น `schema_migrations`), login ของเว็บถูกจำกัดสิทธิ์ (`db/verify-security.mjs`)
- ตัวนับของโมเมนต์ (ไลก์ คอมเมนต์ บันทึก) และกลุ่มไปงาน ตรงกับแถวจริงทุกแถว
- ข้อมูลหลักแยกตารางและบันทึกทีละแถวแล้ว (BE-302) และ `app_settings` เหลือแค่ 4 ค่าเล็กๆ

## รายการแก้ เรียงตามผลกระทบ

### 1. ~~XP ยังไม่มีบัญชีจริง: แลกพร้อมกันสองอย่างแล้ว XP ติดลบได้~~ แก้แล้ว BE-315 (เช็กยอดกับบันทึกการแลกอยู่ใน transaction เดียวใต้ล็อกต่อสมาชิก ทดสอบสองคำขอพร้อมกันแล้ว ผ่านหนึ่ง ปฏิเสธหนึ่ง) ส่วนบัญชี xp_ledger เต็มรูปแบบทำพร้อม "หลายสิทธิ์ต่อแคมเปญ"
ยอด XP คิดใหม่ทุกครั้งจากความคืบหน้าลบด้วยการแลก (`lib/social/rewardsLedger.ts`) ฐานกันได้แค่ "รางวัลเดียวกันซ้ำ" ถ้าแลกรางวัลต่างกันสองอย่างพร้อมกัน ทั้งสองคำขอผ่านเช็กยอดได้ ระบบหลายสิทธิ์ที่ตกลงไว้จะทำให้เกิดง่ายขึ้นอีก
ตาราง `xp_ledger` และ `member_stats` ออกแบบไว้แล้ว (มี `xp_balance >= 0`) แต่ยังว่าง
**แก้:** ได้หรือใช้ XP = เขียนแถวใน `xp_ledger` และปรับ `member_stats` ใน transaction เดียว ฐานจะปฏิเสธการใช้เกินยอดเอง ของรางวัลย้ายจาก `data/rewardsData.ts` ไปอ่านจาก `app.rewards` (บนฐานจริงมี 12 แถวแล้ว) และเพิ่มช่องหลายสิทธิ์ ทำคู่กับ "ของรางวัลในแอดมิน" และ "หลายสิทธิ์ต่อแคมเปญ"

### 2. ~~ทุกการอ่านสมาชิกดึงรหัสผ่านที่เข้ารหัสไว้มาด้วย (ความปลอดภัย)~~ เสร็จแล้ว BE-309
query สมาชิกหลัก (`lib/members/pgMemberRepository.ts` บรรทัด 19) join `member_credentials` ทุกครั้ง บนฐานจริงถูกเรียก 35,686 ครั้ง ค่า `passwordHash` จึงอยู่ในทุก object สมาชิก ถ้าเส้นทางไหนลืมตัดออก ค่านี้จะหลุดไปถึงผู้ใช้
**แก้:** อ่าน hash เฉพาะตอน login และตอนเปลี่ยนรหัส ไม่ต้องเขียน migration

### 3. ตี้ อีเวนต์ และชาเลนจ์ เก็บข้อมูลไว้สองที่ (ส่วนที่อันตรายแก้แล้ว BE-316: ค่าเรื่องการมองเห็น ความปลอดภัย และที่นั่ง อ่านจากคอลัมน์ก่อน ส่วนการลบสำเนาออกจาก details ทำพร้อมข้อ 9)
ทั้ง object อยู่ใน `details` และคอลัมน์เป็นแค่สำเนา ตอนอ่านใช้ `details` ตัวอย่างคือ หน้ารายการสถานที่กรองด้วย `details->>'publicationStatus'` ทั้งที่มีคอลัมน์ `publication_status` อยู่แล้ว ถ้ามีใครแก้คอลัมน์ตรงๆ ค่าใน `details` จะทับตอนอ่าน วันนี้ข้อมูลยังตรงกันครบ (เช็กแล้ว 0 แถวที่ต่างกัน) แต่ที่ตรงได้เพราะทุกการเขียนต้องผ่านการเขียนทั้ง object
- สถานที่: สำเนาใน `details` คือ province, latitude/longitude, publicationStatus, popularity, rating, reviewsCount, district, meetupAllowed, curation และ contact/facilities/highlights ซึ่งมีคอลัมน์ของตัวเองอยู่แล้ว
- ชาเลนจ์: rule, brandReward, steps, startDate/endDate, status, visibility, isOfficial, rewardPoints, category, badgeIcon, image และยังมีค่าที่คิดมาแล้วและเก่าได้ (progressPercent, current, total, participantsCount, completedCountInfo)
- ตี้/อีเวนต์: province, status, maxParticipants, latitude/longitude, registrationOpen, locationType, moderatedAt และ id ที่ชี้ไปตารางอื่น (createdByMemberId, hostId, seriesId, spotId)

**แก้:** ใส่ field เหล่านี้ในรายการ `*_EXACT` ใน `lib/db/postgres/rows.mjs` (อ่านจากคอลัมน์) แล้วใช้ migration ลบออกจาก `details` ทำทีละตาราง: ชาเลนจ์ → ตี้/อีเวนต์ → สถานที่ ข้อนี้ต้องทำก่อนข้อ 9

### 4. ~~เช็ก "ข้อมูลเปลี่ยนไหม" กินเวลาฐานมากที่สุดรองจากการอ่านทั้งตาราง~~ เสร็จแล้ว BE-310 (0035 รันบนฐานจริงแล้ว 8 พ.ย.)
`readIfChanged` นับทุกแถวและรวมเวลาของทุกแถว: กับสถานที่ใช้ 153 ms ต่อครั้ง เรียกไป 1,402 ครั้ง (รวม 215 วินาที) ตี้และชาเลนจ์ก็ทำแบบเดียวกัน รวมถึง `lib/masterDataTables.ts` ด้วย
**แก้:** ตารางเล็ก `app.table_versions (name, version)` ที่ trigger ระดับ statement เพิ่มเลขทุกครั้งที่เขียน การเช็กจะเหลืออ่านแถวเดียวด้วย key (ต่ำกว่า 1 ms)

### 5. ~~`place_images` ไม่มีใครอ่าน แต่ถูกเขียนใหม่ทุกครั้งที่บันทึกสถานที่~~ เสร็จแล้ว BE-312 (0036)
มี 11,712 แถว ขนาด 6.6 MB เขียนเข้า 90,448 ครั้งและลบ 31,888 ครั้ง ส่วนรูปที่หน้าเว็บใช้อ่านจาก `details.galleryImages`
**แก้:** ลบตารางนี้ทิ้ง (รูปเป็นรายการ URL ที่ไม่เคยใช้กรอง เก็บใน details ก็พอ) แบบนี้การบันทึกสถานที่จะเบาลงมาก

### 6. ~~ตารางและสถานะที่เลิกใช้แล้ว~~ เสร็จแล้ว BE-312 (0036) ยกเว้นการรวมรายงานโมเมนต์ที่ไม่เร่ง
- `rate_limit_hits` (ถูกแทนด้วย `rate_limits`), `api_usage` (มีแค่สคริปต์ import ที่ใช้) และ `import_runs` (ไม่เคยเขียน เพราะผลการดึงข้อมูลเก็บใน `sources.extra.lastRun*`): ลบ หรือย้าย lastRun* ไปเก็บใน `import_runs` ถ้าอยากเห็นประวัติ
- `event_participants` มีสถานะ `waitlisted`/`offered` และ index ของรายชื่อรอ แต่โค้ดใช้ตาราง `event_waitlist`: เอาสถานะกับ index ที่ไม่ได้ใช้ออก
- รายงานโมเมนต์อยู่สองที่ (`moment_reports` สำหรับซ่อนอัตโนมัติ และ `content_reports` สำหรับคิวทีมงาน): ค่อยรวมทีหลังได้ ไม่เร่ง

### 7. ~~`participants_count` ใช้ในสองความหมาย~~ เสร็จแล้ว BE-313/314 (0037): นับเฉพาะสมาชิกที่เข้าร่วม ไม่นับเจ้าของตี้ (เจ้าของสั่ง 8 พ.ย.)
ตี้ 1 อันที่ไม่ใช่ข้อมูลตัวอย่างมีตัวเลขมากกว่าแถวคนเข้าร่วม 1 คน (น่าจะนับเจ้าของตี้ด้วย) ส่วนอีเวนต์ 83 อันมีตัวเลขแต่ไม่มีแถวคนเข้าร่วมเลย
**แก้:** ตัดสินว่าเจ้าของตี้นับหรือไม่ แล้วเขียนกฎลงใน CHECK หรือเอกสาร สำหรับอีเวนต์ ถ้าเป็นจำนวน "สนใจ" ให้ใช้ชื่อคอลัมน์ของตัวเอง หรือตั้งเป็น 0 (กฎของหน้าอีเวนต์บอกว่าไม่แสดงจำนวนคนอยู่แล้ว)

### 8. Index ที่รอ query ซึ่งยังไม่มีอยู่จริง และเก็บกวาดเล็กๆ (CHECK ของ sponsored_slots เสร็จใน 0036; index เก็บไว้ให้ข้อ 9)
- มี index ที่ไม่เคยถูกใช้ เพราะรายการกรองกันในหน่วยความจำ: `places_browse_idx`, `places_curation_idx`, `places_vibes_idx`, `events_location_idx`, `moments_search_trgm_idx`, `members_name_trgm_idx`, `quests_live_idx`, `quests_sort_idx` จะลบ หรือเก็บไว้ให้ข้อ 9 ใช้ก็ได้ ส่วน index ของ foreign key และ unique ให้เก็บไว้ แม้ยังไม่ถูกใช้
- `sponsored_slots`: `pillar` ยังไม่มี CHECK และ `item_id` ยังไม่ชี้ตารางไหน
- `sources.extra.lastRun*` ควรเป็นคอลัมน์ ถ้าแอดมินต้องเรียงหรือกรองด้วยค่านี้

### 9. รายการยังอ่านทั้งตารางแล้วกรองในหน่วยความจำ (ขั้น 7 ของ checklist) เลื่อนไว้ 8 พ.ย.: หลัง BE-310 อ่านทั้งตารางเฉพาะเมื่อข้อมูลเปลี่ยน และเป็นงานที่เสี่ยงที่สุด ทำเมื่อคนใช้เยอะขึ้น
สถานที่ทั้งตาราง (`select * from app.places`) คือ query ที่ใช้เวลารวมมากที่สุดบนฐานจริง: 887 ครั้ง × 407 ms และส่งออก 1.9 ล้านแถว ตี้และชาเลนจ์ก็อ่านแบบนี้เหมือนกัน BE-277 ลดลงไปแล้วด้วยการแชร์แคช แต่ยังต้องอ่านทั้งก้อนเมื่อข้อมูลเปลี่ยน
**แก้:** หลังข้อ 3 ให้หน้ารายการและหน้าค้นหาใช้ SQL ที่กรองและแบ่งหน้าเลย พร้อม index ในข้อ 8 ส่วนหน้าทีมงานยังอ่านเต็มได้
